## 1. 项目背景

Cloudflare、CloudFront、Fastly 等 CDN 使用任播网络，同一个域名背后的 IP 在不同地区、不同运营商、不同时间下的表现差异很大。公开的“优选 IP 列表”通常来自别人的网络视角，对你本地网络不一定有效，也可能已经过期。

现有三类项目分别只解决了一部分问题：

| 项目类型 | 已解决的问题 | 对本项目不够完整的地方 |
|---|---|---|
| CloudflareSpeedTest | 在当前网络视角下批量测试 IP 的延迟、丢包、下载速度 | 一次性 CLI 工具，无调度、无历史、无 API、无 DNS 自动化 |
| cf-speed-dns | 定时测速、展示结果、更新 DNS、发送通知 | 依赖 GitHub Actions 与外部站点，控制能力和可审计性弱 |
| ipdb | 对外发布分类 IP 数据，接口简单易用 | 数据来源和测速视角不完全属于你，缺少本地自主测速闭环 |

因此，本项目的核心定位是：

> 在你自己的 192.168.2.6 服务器上持续测速、评分、保存历史、发布结果，并可选择把最优 IP 自动写入 DNS 或暴露 API 给其他设备消费。

## 2. 目标与非目标

### 2.1 核心目标

1. **本地视角**：所有测速都从 192.168.2.6 的实际网络出口发起，避免使用别人网络测出的“假优选”。
2. **自动化**：定时测速、自动评分、自动发布结果，必要时自动更新 DNS。
3. **可解释**：每个推荐 IP 都能追溯到一次测速任务，保留延迟、丢包、下载速度、地区码、测速时间等证据。
4. **可回滚**：DNS 变更前保存旧记录，变更失败或结果异常时可以恢复，避免“优选器”把业务域名解析搞坏。
5. **轻量部署**：适配 ARM64、无 Docker、低资源服务器；部署应为二进制/脚本 + systemd，而不是容器。
6. **可扩展**：IP 池、DNS 提供商、通知渠道、评分权重、输出格式均通过配置扩展。

### 2.2 非目标

- 不做破解、翻墙节点搭建、流量转发或代理服务。
- 不承诺绕过运营商或目标站点限制。
- 不默认做多地域分布式测速；如确有需求，应作为后续独立扩展。
- 不默认接入所有 DNS 提供商；首版只实现你确认使用的提供商。

## 3. 使用场景假设

### 场景 A：动态 DNS 优选

服务器定时测速后，把最优 N 个 IPv4/IPv6 写入你的域名 A/AAAA 记录。客户端始终访问固定域名，实际解析到当前网络下质量更好的 IP。

**适用条件**：
- 你拥有域名和 DNS API 权限。
- 希望手机、路由器、其他服务无需手动改配置。

### 场景 B：本地 API / 文件输出

服务器只发布 `top.txt`、`top.csv`、JSON API，由你的其他系统自行取用。

**适用条件**：
- 不想给 DNS API 权限。
- 消费方是脚本、路由器、OpenClash、配置生成器等。

### 场景 C：Web 面板人工观察与手动触发

提供局域网页面，查看最新结果、历史趋势、任务日志，并可手动触发测速。

**适用条件**：
- 你需要观察 IP 质量变化。
- 需要在变更前人工确认。

> 默认方案建议同时支持 B 和 C；A 需要你确认 DNS 信息后开启。

## 4. 已确认的部署约束

| 项 | 内容 |
|---|---|
| SSH | `192.168.2.6:22`，root，密码已知 |
| CPU 架构 | ARM64 / aarch64 |
| 容器 | 不支持 Docker |
| 部署方式 | 原生二进制或脚本 + systemd |
| 网络 | NAT 服务器；具体可用入站端口待确认 |
| 存储位置 | 本地文件或 SQLite |
| 运行方式 | 常驻服务 + 定时调度，或 systemd timer 调用 CLI |

### 需要现场确认的部署项

1. Linux 发行版和版本。
2. systemd 是否可用。
3. 服务器可用内存、CPU 核数、磁盘剩余空间。
4. NAT 环境下是否已有可转发的 HTTP/HTTPS 端口。
5. 服务器实际网络出口与使用优选 IP 的设备是否在同一网络视角。
6. 服务器是否允许长时间占用下载带宽进行测速。

## 5. 核心业务流程

```text
配置加载
   ↓
IP 池获取 / 更新
   ├─ Cloudflare 官方 IPv4 / IPv6 段
   ├─ 本地 CIDR / 单 IP 文件
   └─ 可选：第三方或反代 IP 列表
   ↓
候选 IP 采样与去重
   ↓
连通性测速
   ├─ TCPing：TCP 握手延迟、丢包
   └─ HTTPing：HTTP 状态、TTFB、地区码
   ↓
可选下载测速
   ↓
过滤与评分
   ├─ 延迟范围、丢包率、下载速度、地区码
   ├─ 历史稳定性
   └─ 黑名单 / 白名单
   ↓
结果落库
   ↓
结果发布
   ├─ Web 页面
   ├─ REST API
   ├─ text / CSV / JSON 文件
   └─ DNS A/AAAA 记录
   ↓
通知与审计
```

## 6. 功能需求

优先级定义：

- **P0**：MVP 必须，不实现则系统不可用。
- **P1**：生产可用必须，建议首版完成。
- **P2**：体验增强，可延后。
- **P3**：暂缓，仅保留接口或设计空间。

### FR-001 IP 池管理 · P0

**用户故事**  
作为使用者，我希望系统可以维护多个 IP 来源，并能限定测速范围，避免测试无关 IP。

**需求细节**

1. 支持 IPv4 与 IPv6。
2. 支持 CIDR、单 IP、本地文本文件。
3. 默认内置 Cloudflare 官方 IPv4/IPv6 地址段。
4. 支持黑名单和白名单。
5. 支持禁用/启用某个来源。
6. 支持记录每个 IP 的来源标签，例如 `official-cf`、`custom`、`external-list`。
7. IP 池变更不能直接删除历史结果。

**验收标准**

- [ ] 配置中添加 `104.16.0.0/13` 后，测速任务可以生成候选 IP。
- [ ] 黑名单 IP 不会被推荐。
- [ ] 每个结果能回溯来源。
- [ ] IPv4 与 IPv6 不混入错误的记录类型。

**用户故事**

5. 支持并发数上限。

**验收标准**

- [ ] 默认采样模式下，一次任务的候选数量可预测。
- [ ] 服务器 CPU 和网络占用不因任务失控。
- [ ] 开启全量测试时，系统能明确提示耗时和风险。

### FR-003 连通性与延迟测速 · P0

**用户故事**  
作为使用者，我希望知道每个 IP 在本地网络下的真实延迟和丢包情况。

**需求细节**

1. 支持 TCPing。
2. 支持 HTTPing。
3. 支持指定端口，默认 443。
4. 支持指定测速 URL。
5. 支持每个 IP 的测试次数，默认 4。
6. 输出指标：
   - 发送次数
   - 接收次数
   - 丢包率
   - 平均延迟
   - 最大/最小延迟或抖动（建议新增）
   - HTTP 状态码
   - Cloudflare colo / IATA 地区码
7. HTTPing 需校验有效状态码，默认 200/301/302。

**验收标准**

- [ ] TCPing 模式不依赖 HTTP URL。
- [ ] HTTPing 模式能识别返回码和地区码。
- [ ] 延迟单位统一为毫秒。
- [ ] 超时 IP 不会造成任务卡死。

### FR-004 下载测速 · P0/P1

**用户故事**  
作为使用者，我希望在延迟合格的 IP 中进一步筛选带宽表现更好的 IP。

**需求细节**

1. 先延迟测速，再对前 N 名做下载测速。
2. 支持配置：
   - 下载测速数量
   - 单 IP 下载时长
   - 最低下载速度
   - 测速 URL
3. 输出 MB/s，保留两位小数。
4. 可禁用下载测速。
5. 下载测速应限制并发，避免轻量服务器带宽被打满。

**验收标准**

- [ ] 禁用下载测速时按延迟排序。
- [ ] 启用下载测速时按速度或综合评分排序。
- [ ] 下载失败不影响延迟数据入库。
- [ ] 下载 URL 不可用时任务能给出明确错误。

**优先级说明**：如果首版只想快速上线，可先实现延迟测速，把下载测速作为 P1。

### FR-005 结果评分与过滤 · P0

**用户故事**  
作为使用者，我希望“优选”不是简单取第一个结果，而是按可配置规则计算。

**需求细节**

1. 支持硬过滤：
   - 最大延迟
   - 最小延迟
   - 最大丢包率
   - 最低下载速度
   - 指定地区码
   - 排除地区码
2. 支持综合评分，建议公式：
   - `score = latency_score * w1 + loss_score * w2 + speed_score * w3 + stability_score * w4 + region_bonus`
   - 权重和地区加分必须可配置。
3. 支持历史稳定性：最近 N 次测速中是否持续可用。
4. 支持防抖动：
   - 只有当新候选显著优于当前推荐时才替换。
   - 支持配置改进阈值，例如 20%。
5. 支持固定推荐 IP 数量，例如 Top 1、Top 5、Top 10。

**验收标准**

- [ ] 相同输入下评分可复现。
- [ ] 每个推荐结果都有 score 和过滤原因。
- [ ] 无合格 IP 时不清空当前推荐，除非明确配置允许。

### FR-006 数据存储与历史 · P0/P1

**用户故事**

**验收标准**

- [ ] 服务重启后历史不丢失。
- [ ] 可按时间查询结果。
- [ ] 数据保留策略能自动清理旧记录。
- [ ] 敏感配置不会明文写入日志。

### FR-007 结果发布 · P0

**用户故事**  
作为使用者，我希望路由器、脚本或浏览器都能用合适格式读取优选结果。

**需求细节**

1. 静态文件：
   - `/top.txt`：每行一个 IP
   - `/top10.txt`：前 10 个 IP
   - `/result.csv`：完整明细
   - `/result.json`：结构化数据
2. REST API：
   - 查询最新推荐
   - 查询历史任务
   - 触发测速
   - 查看健康状态
3. 支持 `type=bestcf`、`country=true`、`down=true` 这类 IPDB 风格参数。
4. 支持输出地区信息，例如 `1.2.3.4#HKG`。
5. API 响应必须包含 `generated_at`，避免客户端误用过期数据。

**建议 API**

```text
GET /health
GET /api/v1/status
GET /api/v1/recommendations
GET /api/v1/results/latest
GET /api/v1/runs?limit=20
GET /api/v1/runs/{run_id}
POST /api/v1/run
POST /api/v1/dns/preview
POST /api/v1/dns/apply
GET /top.txt
GET /top10.txt
GET /result.csv
GET /result.json
```

**验收标准**

- [ ] 无认证时只暴露只读接口。
- [ ] 触发型接口必须鉴权。
- [ ] 文件和 API 的数据来自同一份持久化结果。
- [ ] 结果为空时返回明确状态，而不是 500。

### FR-008 DNS 自动更新 · P0/P1，取决于你的选择

**用户故事**  
作为使用者，我希望域名始终解析到当前网络下更好的 IP，且变更安全可回滚。

**需求细节**

1. 支持至少一种你实际使用的提供商：
   - Cloudflare DNS API
   - DNSPod / 腾讯云 DNS
   - 阿里云 DNS（可后置）
2. 支持 A/AAAA 记录。
3. 支持每条记录写入多个 IP。
4. 支持 TTL 与 proxied 配置。
5. 更新策略：
   - 仅推荐显著变好时更新
   - 当前推荐仍可用则不更新
   - 无新结果时保留旧值
   - 可手动预览和确认
6. 变更前保存旧记录。
7. 变更失败自动回滚。
8. 更新后查询 DNS 验证生效情况。
9. Token 只允许使用最小权限，只开放指定 Zone 的 DNS 编辑权限。

**验收标准**

- [ ] dry-run 可以预览将新增、修改、删除的记录。
- [ ] apply 失败时不会留下半更新状态。
- [ ] 审计日志包含新旧 IP，不包含 Token。
- [ ] DNS 更新失败不影响本地测速和结果发布。

## 8. 推荐技术架构

### 推荐：Go 单二进制

```text
cfip-optimizer
├─ scheduler      定时调度与互斥锁
├─ engine         测速核心，吸收 CloudflareSpeedTest
├─ scorer         评分、过滤、防抖
├─ store          SQLite/文件持久化
├─ publisher      text/csv/json 快照输出
├─ dns            Cloudflare/DNSPod provider
├─ web            HTTP API + 内嵌静态页面
├─ notify         通知渠道
└─ config         YAML + 环境变量
```

优点：

- 与上游 CloudflareSpeedTest 同语言，便于吸收测速逻辑。
- 单二进制适合 ARM64 轻量服务器。
- 无 Python/Node 运行时依赖。
- systemd 管理简单。
- Web/API/调度/存储可以共享同一个进程模型。

备选方案：

| 方案 | 优点 | 缺点 |
|---|---|---|
| Go CLI + Python Flask | 便于借用 cf-speed-dns 的 Python 逻辑 | 双运行时，部署复杂 |
| Shell + systemd timer | 极简 | 状态管理、API、安全、回滚能力弱 |
| Rust 重写 | 性能好 | 与上游代码复用度低，开发成本高 |

### 版权与复用策略

| 上游 | 许可证 | 复用策略 |
|---|---|---|
| CloudflareSpeedTest | GPL-3.0 | 若复制或修改其源码，本项目需 GPL-3.0，并保留版权与来源 |
| cf-speed-dns | 未在仓库中提供 LICENSE | 不能直接复制代码；只借鉴流程与接口设计，重新实现 |
| ipdb | MIT | 可复用数据/接口设计，需保留 MIT 声明与归属 |

> 需要你确认：如果希望私有闭源发布，就不能直接复制 CloudflareSpeedTest 源码，应改为自研测速引擎；如果接受 GPL-3.0，则可以最大化复用成熟实现。

## 10. 当前必须确认的核心问题

这些问题会直接决定功能边界和实现顺序。

### Q1 使用目的

你最终要的是哪种？

1. **自动更新 DNS**：给我域名和 DNS 服务商，我直接维护 A/AAAA。
2. **只提供 API/文件**：不改 DNS，由你的其他系统消费。
3. **两者都要**：先 API，DNS 通过 dry-run 确认后启用。

### Q2 网络视角

192.168.2.6 的网络出口，是否就是实际使用这些优选 IP 的网络视角？

- 是：测速结果对使用场景有效。
- 否：需要改为在路由器/主用设备附近部署，或增加多节点测速。

### Q3 IP 范围

首版测哪些？

- 仅 Cloudflare 官方 IPv4
- Cloudflare 官方 IPv4 + IPv6
- 官方 + 自定义 CIDR
- 官方 + 第三方反代 IP 列表

### Q4 评分口径

你更重视什么？

- 延迟优先
- 下载速度优先
- 稳定性优先
- 指定地区优先，例如 HKG/NRT/LAX/SJC
- 自定义权重

### Q5 DNS 信息

- 主域名
- 子域名
- 每个子域名保留几个 IP

- 是否允许删除多余记录
- 是否 proxied

### Q6 运行频率

- 每 30 分钟
- 每 1 小时
- 每 6 小时
- 每天固定时间
- 仅手动

### Q7 Web/API 暴露方式

- 只监听 192.168 内网
- 通过 NAT 端口暴露
- 是否需要登录
- 目标端口

## 12. 风险清单

| 风险 | 影响 | 缓解 |
|---|---|---|
| 服务器网络视角与实际使用设备不同 | 优选结果无效 | 先确认 Q2，必要时迁移部署位置 |
| 轻量服务器带宽小 | 下载测速慢或影响其他业务 | 限制下载并发、延长周期、默认关闭下载测速 |
| NAT 无可用端口 | Web/API 无法访问 | 只用 SSH 隧道，或仅输出文件 |
| DNS 自动更新误操作 | 域名解析异常 | dry-run、最小权限、审计、回滚 |
| 公开测速 URL 不可用 | 结果缺失或下载速度为 0 | 支持自建 URL 与健康检查 |
| 历史数据膨胀 | 磁盘占满 | 保留策略和磁盘告警 |
| 上游许可证冲突 | 无法按期望开源/闭源 | 编码前确认 GPL 接受度 |
