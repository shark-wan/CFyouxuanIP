- 版本：v0.9

本文回答三个问题：

2. 它们的能力如何原子化拆分？

## 1. 上游项目核心分析

### 1.1 XIU2/CloudflareSpeedTest

**核心问题**  
从当前网络视角出发，测试一组 CDN IP 的 TCP/HTTP 延迟、丢包和下载速度，找出可用且速度好的 IP。

**能力亮点**

| 能力 | 具体表现 |
|---|---|
| 高并发测速 | 默认 200 线程，可调，适合扫描大范围 IP |
| TCPing | 测试 TCP 握手延迟，不依赖 HTTP 内容 |
| HTTPing | 通过真实 HTTP 请求测试，并识别 `cfcolo` |
| 下载测速 | 对延迟测试前 N 名继续测速 |
| 过滤条件 | 延迟上下限、丢包率、下载速度、地区码 |
| IPv4/IPv6 | 支持两套地址段 |
| 自定义 IP | 支持 CIDR、单 IP、文件 |
| 结果输出 | 控制台、CSV |
| 低依赖 | Go 二进制，适合 ARM64 |

**不足**

- 一次性 CLI，没有常驻调度。
- 结果只落 CSV，没有历史数据库。
- 无 API、无 Web 面板。
- 无 DNS 更新闭环。
- 无通知、健康检查、回滚。
- 参数较偏工程使用，不适合普通用户持续运营。

**对新项目的价值**

- 作为测速引擎的核心参考或直接复用基础。
- 参数设计应转换成 YAML 配置。
- 输出结构应从 CSV 扩展为结构化结果。
- 需要补上状态、调度、发布和 DNS 闭环。

**许可证**：GPL-3.0。

---

### 1.2 ZhiXuanWang/cf-speed-dns

**核心问题**  
让 CloudflareSpeedTest 的结果持续对外可用，并自动写入 DNS 记录。

**能力亮点**

| 能力 | 具体表现 |
|---|---|
| 自动化调度 | 通过 GitHub Actions 定时执行 |
| DNS 更新 | 支持 Cloudflare API 和 DNSPod API |
| 结果页面 | 静态 HTML 展示测速结果 |
| 简单接口 | `ipTop.html`、`ipTop10.html` 直接返回 IP |
| 通知 | PushPlus 消息推送 |
| 免服务器 | 可在 GitHub Actions 上跑 |

**不足**

- 依赖 GitHub Actions，不适合本地私有部署。
- 测速网络视角是 GitHub runner 或其外部站点视角，不一定是你的本地视角。
- 结果管理简单，缺少历史和审计。
- DNS 更新缺少事务性 diff 和回滚。
- 通知渠道单一。
- 仓库未提供许可证，不能直接复制源码。

**对新项目的价值**

- 借鉴“测速 → 发布 → DNS → 通知”的完整流程。
- 借鉴简单接口设计：Top 1 / Top 10 文本接口。
- 借鉴 DNS 提供商抽象。
- 需将 GitHub Actions 调度改为本地 systemd/内置调度。

---

### 1.3 ymyuuu/ipdb

**核心问题**  
将不同来源、不同类型的 IP 数据统一分类，并通过简单 API/文件对外发布。

**能力亮点**

| 能力 | 具体表现 |
|---|---|
| 数据分类 | `cfv4`、`cfv6`、`proxy`、`bestcf`、`bestproxy` 等 |
| API 参数 | `type`、`country`、`down` 简单直观 |
| 多格式输出 | 文本、带国家信息文本、CSV 数据 |
| 多账号 | Workflow 支持多个 Cloudflare Token |
| 批量 DNS | 可以将 IP 列表写入多个子域名 |
| 更新频率清晰 | 不同类型数据有不同刷新周期 |

**不足**

- 优选结果主要来自公开流程或外部视角，不一定匹配你的本地网络。
- 仓库本身主要是数据和 GitHub Workflow，不是完整本地服务。
- 对私有化部署、权限控制、回滚支持不足。
- 无法保证数据对你当前网络有效。

**对新项目的价值**

- 借鉴 API 设计和结果分类。
- 借鉴“下载文件 vs 直接返回内容”的参数。
- 借鉴多子域名、多记录批量更新设计。
- 增加本地测速，使 `bestcf` 变成真正由你自己的服务器测出的结果。

**许可证**：MIT。

## 2. 合并后的核心问题定义

三个项目合并后，新系统要解决一条完整链路：

```text
“从我的网络视角测速”
→ “筛选出可持续使用的最优 IP”
→ “保存证据和历史”
→ “发布给页面/API/文件”
→ “可选写入 DNS”
→ “通知异常并支持回滚”
```

它们分别对应：

| 环节 | 最强上游 |
|---|---|
| 测速 | CloudflareSpeedTest |
| DNS 与自动化流程 | cf-speed-dns |
| API/数据发布与分类 | ipdb |
| 安全、历史、回滚、运维 | 新增设计 |

## 4. 新项目模块设计

推荐采用 Go 单二进制：

```text
cmd/cfip-optimizer/       程序入口
internal/config/          配置加载、环境变量替换、校验
internal/ip_pool/         IP 来源、解析、去重、黑白名单、采样准备
internal/engine/          TCPing、HTTPing、下载测速
internal/scorer/          过滤、评分、排序、防抖
internal/store/           SQLite、历史、审计、保留策略
internal/publisher/       top.txt、top10.txt、CSV、JSON 快照
internal/dns/             provider 抽象、diff、apply、rollback
internal/web/             HTTP API、静态页面、鉴权
internal/scheduler/       定时任务、锁、超时、取消
internal/notify/          通知渠道
internal/logging/         日志
web/                      前端静态资源
configs/config.example.yaml
scripts/install.sh
scripts/upgrade.sh
systemd/cfip-optimizer.service
```

### 4.1 config

**职责**

- 加载 YAML。
- 展开 `${ENV}`。
- 校验必填项和取值范围。
- 生成不可变配置快照。
- 提供默认值。

**不负责**

- 保存密钥到数据库。
- 修改业务状态。

### 4.2 ip_pool

**输入**

```yaml
sources:
  - type: builtin
    name: cloudflare-v4
  - type: file
    path: /etc/cfip/custom.txt
    tag: custom
```

**输出**

```go
type Candidate struct {
    IP       string
    Version  int    // 4 or 6
    Source   string
    Priority int
}
```

**关键点**

- 必须去重。
- 必须区分 IPv4/IPv6。
- 黑名单优先级最高。
- 每次运行生成候选快照，便于审计。

### 4.3 engine

**输入**

```go
type TestConfig struct {
    Mode         string
    Port         int
    URL          string
    Routines     int
    PingTimes    int
    Timeout      time.Duration
    AllowedCodes []int
    Regions      []string
}
```

**输出**

```go
type IPTestResult struct {
    IP            string
    Version       int
    Source        string
    Sent          int
    Received      int
    LossRate      float64
    AvgLatencyMS  float64
    MinLatencyMS  float64
    MaxLatencyMS  float64
    JitterMS      float64
    DownloadMBps  float64
    HTTPStatus    int
    Colo          string
    Error         string
}
```

**与上游关系**

- 可复用或参考 CloudflareSpeedTest 的 `task/tcping.go`、`task/httping.go`、`task/download.go`、`task/ip.go`。
- 需将 CSV 输出改为结构化数据。
- 需把全局变量改为显式配置对象。
- 需增加超时和取消传播。
- 需要适配轻量 ARM64 服务器的默认并发。

### 4.4 scorer

**处理顺序**

```text
硬过滤
→ 指标归一化
→ 加权评分
→ 历史稳定性修正
→ 防抖比较
→ Top N
```

**示例评分**

```text
latency_score = clamp(1 - avg_latency / max_latency, 0, 1)
loss_score    = 1 - loss_rate
speed_score   = clamp(download_speed / target_speed, 0, 1)
stability     = recent_success_count / recent_total

score =
  0.4 * latency_score +
  0.3 * loss_score +
  0.2 * speed_score +
  0.1 * stability +
  region_bonus
```

**必须输出 reason**

例如：

```text
pass: avg_latency 45ms, loss 0%, colo HKG, speed 8.2MB/s, stability 5/5
```

### 4.5 store

**职责**

- 写入测速任务。
- 写入 IP 明细。
- 维护 active recommendation。
- 保存 DNS 变更审计。
- 数据清理。

**存储策略**

| 方案 | 优点 | 缺点 |
|---|---|---|
| SQLite | 查询和历史能力强 | 需要驱动依赖 |
| JSON/CSV | 简单、可直接备份 | 查询和历史趋势弱 |
| SQLite + 文本快照 | 推荐 | 需要保持一致性 |

### 4.7 dns

**Provider 接口**

```go
type Provider interface {
    ListRecords(ctx context.Context, zone string, name string) ([]Record, error)
    ApplyChanges(ctx context.Context, zone string, changes Changes) error
    Rollback(ctx context.Context, zone string, changes Changes) error
}

type Changes struct {
    Create []Record
    Update []RecordUpdate
    Delete []Record
}
```

**安全规则**

1. 必须先计算 diff。
2. 默认 dry-run。
3. apply 前保存旧值。
4. apply 失败执行 rollback。
5. 只处理配置中明确允许的 zone、record name、type。
6. 永远不在日志中输出 token。

### 4.8 web

**分层**

```text
router
├─ public read endpoints
├─ auth middleware
├─ protected write endpoints
└─ static embedded UI
```

**写操作**

- POST `/api/v1/run`
- POST `/api/v1/dns/preview`
- POST `/api/v1/dns/apply`
- POST `/api/v1/dns/rollback`

**默认安全**

- 只读接口可匿名。
- 写接口需要 token。
- 管理页面可关闭。
- 可限制监听地址。

### 4.9 scheduler

**状态机**

```text
idle
→ queued
→ running
→ success / failed / timeout / canceled
→ idle
```

**必须保证**

- 全局单任务。
- 服务重启后不重复跑同一个周期。
- 任务超过 max duration 自动失败。
- 停机窗口错过时可配置立即补跑或跳过。

## 5. 关键流程设计

### 5.1 定时测速

```text
scheduler tick
→ 检查互斥锁
→ 创建 test_run
→ 加载 ip_pool
→ engine 测速
→ scorer 过滤评分
→ store 保存
→ publisher 输出
→ 如 dns.enabled 则 dns preview
→ 如允许 auto apply 则 apply
→ notify 异常
→ 更新 test_run 状态
```

### 5.2 DNS 变更

```text
读取 active recommendations
→ provider ListRecords
→ 计算 create/update/delete
→ dry-run 输出 diff
→ 用户或配置允许 apply
→ 保存 old/new
→ 执行变更
→ 失败 rollback
→ 成功后查询验证
→ 写审计
```

### 5.3 手动触发

```text
POST /api/v1/run
→ 鉴权
→ scheduler enqueue
→ 返回 run_id
→ 客户端轮询 /api/v1/runs/{run_id}
```

## 7. MVP 最小闭环

为了保证尽快可用，MVP 只做以下能力：

```text
配置
→ 内置 Cloudflare IPv4
→ HTTPing/TCPing
→ 延迟/丢包过滤
→ Top 10
→ SQLite/文件保存
→ Web 列表 + top.txt + health
→ systemd 常驻
→ ARM64 部署
```

暂缓：

- DNS 自动 apply
- 下载测速
- 通知
- 趋势图
- 多 DNS 提供商
- 第三方 IP 源

这样可以用最小风险验证两个关键问题：

1. 192.168.2.6 的测速视角是否有效。
2. 默认并发和周期是否适合这台轻量服务器。

## 8. 构建与部署设计

### 8.1 构建

```bash
GOOS=linux GOARCH=arm64 CGO_ENABLED=0 \
  go build -trimpath \
  -ldflags "-s -w -X main.version=... -X main.commit=..." \
  -o dist/cfip-optimizer-linux-arm64 \
  ./cmd/cfip-optimizer
```

如使用 SQLite，可选择：

1. `modernc.org/sqlite`：纯 Go，便于 CGO_ENABLED=0 交叉编译。
2. `mattn/go-sqlite3`：成熟但需要 CGO 和交叉编译工具链。

推荐优先使用纯 Go SQLite，降低 ARM64 部署难度。

### 8.2 systemd

```ini
[Unit]
Description=Local Cloudflare IP Optimizer
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=cfip
Group=cfip
WorkingDirectory=/var/lib/cfip-optimizer
ExecStart=/usr/local/bin/cfip-optimizer --config /etc/cfip-optimizer/config.yaml
Restart=on-failure
RestartSec=5
LimitNOFILE=65535

[Install]
WantedBy=multi-user.target
```

### 8.3 目录规划

```text
/etc/cfip-optimizer/config.yaml
/var/lib/cfip-optimizer/cfip.db
/var/lib/cfip-optimizer/public/
/var/log/cfip-optimizer/
/usr/local/bin/cfip-optimizer
/usr/local/lib/systemd/system/cfip-optimizer.service
```

## 9. 复用边界与许可证

| 上游代码/设计 | 是否直接复制 | 原因 |
|---|---|---|
| CloudflareSpeedTest Go 测速实现 | 待确认 | 复制会引入 GPL-3.0 |
| CloudflareSpeedTest 参数与流程设计 | 可以借鉴 | 思想不受版权保护 |
| cf-speed-dns Python DNS 调用 | 不直接复制 | 上游未提供许可证 |
| cf-speed-dns Actions 流程 | 可以借鉴 | 设计思想 |
| IPDB API 参数设计 | 可以借鉴 | 设计思想 |
| IPDB MIT 代码/数据 | 可复用 | 需保留声明 |

**推荐决策**

- 如果你准备开源且接受 GPL-3.0：直接复用 CFST 源码，开发最快、测速行为最成熟。
- 如果你要闭源或自选许可证：重新实现测速逻辑，不复制 CFST 代码。

## 11. 推荐默认决策

如果你没有特别偏好，建议按以下顺序实现：

1. 接受 GPL-3.0，直接基于 CFST 吸收测速引擎。
2. 首版只做 Cloudflare 官方 IPv4。
3. 先启用 HTTPing + 延迟过滤，下载测速可手动触发。
4. 每 6 小时跑一次。
5. 输出 Top 10。
6. SQLite 保留 30 天。
7. Web 只监听内网，写操作使用 token。
8. DNS 默认关闭，先提供 dry-run。
9. 首版通知可选。
10. 部署为 Go ARM64 单二进制 + systemd。
